ScopeGuard

Your AI coding agent says the tests pass. ScopeGuard checks how it got there. It reads the change and flags every test that was skipped, loosened, commented out or deleted, every CI step told to ignore failures, and every file the task never allowed it to touch.

Try it

Pick one of the real-shaped examples, or paste your own change: the output of git diff, git show, or a pull request's .diff link saved as text.

Start here

  1. Press an example above, then Check it. "It skipped the failing test" is the quickest to read: one line, one finding.
  2. Read the verdict. Flagged means at least one high finding: a reviewer must read those lines before the change is merged. Review means only review findings: worth a look, often honest. Clean means no rule fired.
  3. Read each finding. Every one names its rule, the file and line, and the exact text. The rule list below says what each rule looks for.
  4. Paste your own change. In a terminal in your project, run git diff main...HEAD (or git show for the last commit), copy the output, paste it in. Nothing leaves this page.
  5. Add a scope if the task should only touch some files: one allow line per folder or file pattern. Anything else the change touches is flagged.
  6. Put it to work: in CI on every pull request, as a Claude Code hook so the agent cannot finish with a weakened test, or as a pre-commit check. See Put it to work.

Two kinds of rule

Line rules look at one added line: a skip marker, a focus marker, a "continue on error". They only fire when the marker is new: one that was removed and added back (moved, re-indented) is not new.

Pairing rules compare what was removed with what was added in the same file. An exact check (toBe(2500), assertEqual, ==) removed and a looser one (toBeDefined(), assertTrue, !=) added on the same value is a loosened check. The pairing is by the value being checked, so argument order does not matter, and a rename to a different value is not paired. A removed line and an added line that differ only in one number are compared number by number, which is how a widened tolerance or a lowered coverage floor is found.

Measured: how often it cries wolf, and whether it catches what it says

A checker that flags every honest change gets switched off. So before the rules were written, we fixed how they would be judged (CLAIMS.md, committed first): every commit that touches a test or CI file in our own public repositories, split by repository into a half the rules could be tuned on and a half held back and run once, after the code was frozen.

Versions 1.1 and 1.2: the fixes for what version 1 missed

Version 1 missed planted weakenings for three reasons, all real: it treated a CI step as still testing when any command of the same runner stayed (so dropping one gated file from a list went unseen); it counted a check as "still exact" when any exact check on the same value was added (so a generic value like r.why hid a loosened one); and it judged a replaced assertion across the whole file (so an identical line elsewhere hid it). Version 1.1 fixes all three. Version 1.2 then stopped reading a marker inside a string literal as code: found when ScopeGuard checked its own first push, whose tests hold diffs as strings ('+it.skip("adds"...') and were flagged as skipped tests. Because the held-out half had already been read, these versions' figures on it are a re-run, not a held-out result.

What it can't tell you

  • Intent. A flagged line can be honest: a test deleted along with the feature it tested, an expected value changed because the specification changed. The verdict is a list of lines to read, with the reason for each, not an accusation.
  • Weakenings it has no rule for. If the agent changes the code under test so a test passes trivially, or writes a brand-new test that checks nothing useful, no rule here sees it. Pair ScopeGuard with a mutation test (such as witness), which measures whether the tests can fail at all.
  • Whether the tests pass. It reads the change; it does not run anything.
  • Every language equally. The rules know JavaScript and TypeScript (Jest, Vitest, Mocha, node:test, Chai), Python (pytest, unittest), Go (testing, testify), Java and Kotlin (JUnit), C# (NUnit, xUnit), Ruby (RSpec, Minitest), PHP (PHPUnit) and Rust. The honest-data measurement above is mostly JavaScript, because that is what our repositories are written in, and mostly AI-written. Other languages are covered by the rules and their tests, not yet by a measurement on honest changes.
  • Multi-line statements. Rules read one line at a time. An assertion split across several lines is seen through its first line only.
  • Binary files. A binary test or gate file cannot be read, so it is flagged as unreadable rather than passed.
  • Tests moved between files. Rules judge each file on its own. A test moved from one file to another shows as a review finding (assert-net-loss) on the file it left, which does not block by default; a reviewer clears it by seeing the same assertions arrive in the other file.
  • No scope file, no scope rules. Without a .scopeguard file every path is in scope, so only the test and CI rules run. The scope rules need the file (the Action and the Claude Code hook read it from the base commit, never the working copy).

Put it to work

In CI, on every pull request (GitHub Actions)

name: scopeguard
on: [pull_request]
jobs:
  scopeguard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: sjgant80-hub/kar-scopeguard@main   # pin to a commit SHA in production
        with:
          fail-on: high        # or: review

The scope file (.scopeguard in the repository root) is read from the base commit, not from the pull request, so a change cannot widen its own scope. The findings go to the job summary.

As a Claude Code hook: the agent cannot finish with a weakened test

Claude Code runs "Stop" hooks when the agent is about to end its turn. When a Stop hook exits with code 2, the agent is not allowed to stop and is shown the hook's message as the reason. ScopeGuard's hook checks the working tree against the last commit. On a high finding it stops the agent once, lists the lines, and asks it to fix the code instead of the check, or to explain an honest change in its final message. It never stops the agent twice for the same findings, so it cannot trap it in a loop. Review findings never stop it. Put this in .claude/settings.json:

{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "node /path/to/kar-scopeguard/cli.mjs --hook" } ] }
    ]
  }
}

Before each commit

node /path/to/kar-scopeguard/cli.mjs --git --staged

Put that line in .git/hooks/pre-commit. It checks what is staged and exits 2 on a high finding, which stops the commit.

On the command line

git diff main...HEAD | node cli.mjs - --scope .scopeguard
node cli.mjs change.diff --claim summary.txt --json
node cli.mjs --git            # this folder against its last commit, new files included

Exit codes: 0 clean (and review, unless --fail-on review), 2 flagged, 1 the input could not be read or the options were wrong. Node.js 20 or later; nothing to install.

Risks, answered straight

What if it flags honest changes?
It will sometimes. The measured rate is in Measured. A false flag costs a reviewer the time to read the named lines and a sentence of explanation.
What if it misses a weakening?
It can: see What it can't tell you. It is one control. Mutation testing, which checks whether the tests can fail at all, is the natural partner.
Can an agent learn to get round it?
An agent that reads this page could choose weakenings with no rule. That is why the rules are a closed, published list and the verdict is "read these lines", not "this change is safe". Clean means no listed rule fired, nothing more.
Can I trust the code?
Read it: the kernel is one file, and every rule has a test with an example that must fire and one that must not. A mutation gate checks the tests on every change. The first version's rules were tuned on half of our history and still had to pass the held-out half.
Who is accountable for a merge?
Your reviewers. ScopeGuard points; people decide.

The case for the board

AI agents write code faster than people can review it. The specific way that goes wrong is quiet: the agent makes the checks pass by weakening the checks. That failure leaves no trace in a green build. ScopeGuard is a fixed, published control that finds it on every change, costs no licence fee, sends nothing outside the company, and gives an answer anyone can rerun. Its false-alarm rate on honest changes is measured and published, not promised.

The explainer

The problem. A coding agent is trained and prompted to finish tasks, and a task is "finished" when the tests pass. Tests are code, and the agent can edit code. So there are two ways to green: fix the program, or change the test. Agents take the second way often enough that people who supervise them have learnt to look for it, and published evaluations of coding agents have caught it many times: tests skipped, assertions deleted, expected values rewritten to match wrong output, CI told to ignore a failing step.

Why a reviewer misses it. The weakening is usually one line in a large change, and it reads as plausible: toBeDefined() looks like a test. A reviewer looks at what the change does, not at what it stopped checking.

What ScopeGuard does. It reads only the diff, so it works on any change from any agent or person, before anything runs. It sorts each file into test, snapshot, CI/test configuration ("gate") or ordinary code, and checks the path against an optional scope. Then it runs a closed list of rules: markers that stop tests running, assertions turned into comments or into checks that can never fail, exact checks replaced by looser ones on the same value, tolerances widened, coverage floors lowered, test commands removed, failures ignored, test files deleted or renamed out of the runner's reach. Each finding carries its line. A diff it cannot fully read (cut off, combined merge, a binary test file) is refused or flagged, never passed.

Why no AI judge. A model judging a change gives a different answer on a different day and can be talked round by the change itself (a comment saying "this skip is fine"). A fixed rule does neither. The fingerprints (SHA-256 of the exact input and of the result) let anyone confirm, later, that a given change got a given verdict.

How it was checked. The claims were written and committed before the code. The rules were tuned on half of our repositories' history and then run, once, on the other half. Each held-out high finding was read and labelled. Weakenings were planted into real diffs to measure whether each rule fires on real-world diff shapes. Every part is mutation-gated: each file's tests must kill every mutant the gate makes, with none set aside. The counts are in the blueprint, read from receipts/witness.json. All of it is on this page and in the repository.

Words on this page

Diff
The text that shows what a change added (lines starting +) and removed (-). git diff prints one.
Hunk
One block of a diff, starting with @@ -10,4 +10,5 @@: where the block starts and how many lines it has on each side. ScopeGuard checks those counts; a diff whose counts don't add up was cut off or edited, and is refused.
Assertion
The line in a test that checks a result, such as expect(total).toBe(24) or assert total == 24. Remove it and the test checks nothing.
Exact and loose checks
toBe(24) passes for 24 only. toBeDefined() passes for 24, 0, or a wrong answer. Swapping the first for the second makes a test easier to pass without making the code more right.
Gate file
A file that decides whether a change is accepted: CI workflows, test runner and coverage settings, compiler strictness settings, a mutation-test baseline.
Scope
The files a task is allowed to touch, written as patterns in a .scopeguard file.
Mutation gate
A check on the tests themselves: it changes the code on purpose and expects the tests to fail. If they still pass, they were not really testing that line. Every part of ScopeGuard passes one.
Fingerprint (SHA-256)
A 64-character code computed from exact bytes. Change one character and it changes completely. The same diff always gives the same fingerprint, so a saved result can be checked later.
Held-out data
Data kept aside while the rules were written and run once afterwards, so the rules could not be fitted to it. Later versions re-run on the same data are labelled as re-runs.
Stop hook
A command Claude Code runs when its agent is about to finish a turn. If the command exits with code 2, the agent keeps working and sees the command's message.

FAQ

Does it only work on changes made by AI?

No. It reads any diff. People weaken tests too, usually under deadline pressure. It was built for AI agents because they make many changes, fast, and are rewarded for green.

Why are some findings "review" and not "high"?

Because on honest changes they are common. An expected value changes whenever a specification changes, and a mutation baseline grows when a survivor is accepted with a reason. They are listed so a reviewer can read them, but by default they do not fail the build. --fail-on review makes them fail it.

What does the fingerprint prove?

That this exact diff, scope and summary gave this exact result. Run the command line on the same input and you get the same two fingerprints. It does not prove the change is good; it proves what was checked and what was found.

A test was skipped for a good reason. What do I do?

Say why in the pull request. The finding is a request to read the line, not a block on the change. In the hook, the agent is asked to explain it in its final message and is not stopped again for the same finding.

Can I add my own rules?

The kernel is one MIT-licensed file; add a rule with a test that fires and one that does not, and run the mutation gate. Rules are deliberately a closed list in code, not a configuration file, so a change cannot turn a rule off.

Does it support GitLab, Bitbucket or other CI?

Yes, through the command line: git diff "$BASE"...HEAD | node cli.mjs -. Exit code 2 fails the job. The GitHub Action is a convenience around that line.

Why does it read only one line at a time?

Because a diff is lines, and a rule that reads one line is simple enough to test completely. The cost: an assertion split over several lines is seen through its first line only. That is written down above as a limit.
